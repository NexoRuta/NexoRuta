# Auditoría de RLS vigente

**Estado observado:** rama `feature/cu01-gestion-accesos`; auditoría del backend consolidado después del refactor de contratos RLS, no de una versión intermedia. Se revisó la migración aplicada por el código y las pruebas sobre PostgreSQL efímero. No se aplicaron migraciones, no se escribieron datos en PostgreSQL local persistente y no se ejecutó Compose.

En las referencias, la migración citada como `migration:línea` es [`EnablePostgreSqlRls.cs`](../../backend/src/NexoRuta.Infrastructure/Persistence/Migrations/20261017201732_EnablePostgreSqlRls.cs).

## Verificado

### Recorrido de una petición

1. `backend/src/NexoRuta.Api/Program.cs:79-98` configura validación de issuer, audience, firma HS256 y expiración del JWT. El orden real es `UseAuthentication` → `RlsTransactionMiddleware` → `UseAuthorization` → controllers (`Program.cs:214-219`).
2. `JwtValidacionEventos.TokenValidated` toma el usuario y el ID de acceso de la sesión, consulta el acceso persistido y comprueba que pertenezca al usuario y que la versión coincida (`backend/src/NexoRuta.Api/Core/Security/JwtValidacionEventos.cs:12-121`). Trata por separado plataforma, identidad aún sin organización y sesión limitada de organización suspendida; no acepta el ID de organización del request como autoridad.
3. Para una petición autenticada, `RlsTransactionMiddleware` exige un contexto reconocido, abre la transacción, vuelve a consultar el acceso/sesión y confirma que no cambió desde autenticación; solo entonces llama a `ApplyAsync` (`backend/src/NexoRuta.Api/Core/Security/RlsTransactionMiddleware.cs:17-47,67-119`). Respuestas HTTP `>=400` y excepciones revierten; el éxito confirma. El cuerpo se retiene hasta decidir commit/rollback (`:32-65`). Anónimos pasan sin esa transacción (`:17-21`).
4. `RlsActorContext` se deriva de los contextos persistidos de comercio/operador, plataforma, identidad sin organización o sesión suspendida; bootstrap y worker tienen datos específicos separados (`backend/src/NexoRuta.Infrastructure/Persistence/RlsTransaction.cs:11-55`). El enum y el mapeo cerrado a valores SQL están en `RlsContextContract.cs:5-60`; las claves `nexoruta.*` están centralizadas allí (`:16-41`).
5. `ApplyAsync` exige una transacción activa (`RlsTransaction.cs:68-78`). Ejecuta `SELECT set_config(@name,@value,true)` con los valores como parámetros y con la misma transacción/conexión (`:128-195`). El `true` hace que el valor sea local a la transacción. Los repositorios pueden unirse a la transacción existente y no confirman la transacción propiedad del middleware (`:59-66,201-210`). No se encontró un `HasQueryFilter` global en `backend/src`: la protección de filas está en PostgreSQL, no en un filtro EF implícito.
6. El endpoint/EF usa el mismo contexto transaccional. Al commit/rollback, los GUC locales dejan de aplicarse antes de que la conexión pueda reutilizarse. La prueba reutiliza el mismo PID/conexión después de commit y rollback y observa cero envíos sin establecer otro contexto (`RlsPolicyTests.cs:181-258`).

### Roles, funciones y alcance de privilegios

- El dueño de tablas es `nexoruta_schema_owner`; roles de grupo `nexoruta_api`, `nexoruta_worker`, `nexoruta_bootstrap` y dueños `*_fn` se crean como NOLOGIN, NOINHERIT, NOSUPERUSER y NOBYPASSRLS (`migration:17-41,88-111`). La migración revoca los privilegios iniciales de PUBLIC y de roles de runtime antes de las concesiones explícitas (`:509-537`).
- `backend/scripts/provision-rls-runtime-roles.sql:1-76` aprovisiona logins `nexoruta_api_runtime`, `nexoruta_worker_runtime`, `nexoruta_bootstrap_runtime`; cada uno hereda solo su grupo, sin SUPERUSER/BYPASSRLS ni propiedad de objetos. API y workers no heredan dueño de esquema o de funciones.
- Dueños SECURITY DEFINER: lookup de login/accesos → `nexoruta_auth_fn`; tracking público → `nexoruta_public_fn`; creación → `nexoruta_shipment_fn`; cola → `nexoruta_queue_fn`; validación de job → `nexoruta_job_fn`; roles → `nexoruta_role_fn`; suspensión/reactivación y revocación de sesiones → `nexoruta_org_fn` (`migration:492-507`).
- Las funciones fijan `search_path = pg_catalog,nexoruta_app`; los helpers de contexto usan `pg_catalog`. `EXECUTE` se revoca a PUBLIC y se concede a grupos nombrados, no a logins indiscriminados (`:140-507,516-537`). En tablas, los roles dueños de funciones también tienen políticas y grants específicos; no son bypass de RLS. La prueba de catálogo comprueba `proowner`, `rolcanlogin`, `rolsuper`, `rolbypassrls`, ACL de PUBLIC y `proconfig` (`RlsPolicyTests.cs:91-117`).
- `RlsSqlFunctionContractTests.cs` comprueba con conexiones restringidas que las 13 funciones consumidas por C# existen con firma, retorno y `EXECUTE` esperados; también prueba firma/retorno incompatibles y función ausente.

### Recorridos especiales

- **Login:** `EfUsuariosLoginRepository` usa `login_lookup` (`backend/src/NexoRuta.Infrastructure/Administracion/Autenticacion/EfUsuariosLoginRepository.cs:13-30`; SQL `migration:140-257`); Identity valida la contraseña. Para una cuenta sin organización, el lookup dedicado permite hallar la identidad antes del acceso seleccionado. Registro anónimo usa el almacén Identity global (`EfRegistroRepository.cs:16-37`).
- **Cuenta sin organización:** el JWT se contrasta con la identidad persistida y la API pone un `IdentidadSinOrganizacion` verificado en el request; middleware revalida y aplica actor `identidad`. RLS permite solo las filas de acceso/rol necesarias para onboarding, no un tenant arbitrario (`JwtValidacionEventos.cs:40-50`; middleware `:110-117`).
- **Plataforma:** sesión, usuario, versión y acceso se verifican desde `AccesosPlataforma`. La bandera de gestión permite administrar organizaciones y solicitudes, no consultar envíos ni PII (`JwtValidacionEventos.cs:57-66`; `RlsPolicyTests.cs:164-179`).
- **Suspensión/reactivación:** el estado suspendido permite el flujo limitado de solicitud de reactivación; middleware vuelve a comprobar estado, organización, tipo y versión. La función de cambio de estado actualiza la organización y revoca sesiones/avanza versión (`migration:437-490`; `RlsTransactionMiddleware.cs:95-108`).
- **Alta propia:** `EfPlataformaRepository` fija la organización, usuario y rol seleccionados en la misma transacción de alta; las políticas exigen esos IDs (`backend/src/NexoRuta.Infrastructure/Administracion/Repositories/EfPlataformaRepository.cs:93-149`; `migration:622-676`).
- **Creación de envío:** `EfEnviosRepository` ejecuta transaccionalmente `create_shipment`; la función verifica el acceso comercio persistido, bloquea el operador elegido que esté activo e inserta envío, destinatario, dirección y bulto con GUIDs concretos (`backend/src/NexoRuta.Infrastructure/Envios/Repositories/EfEnviosRepository.cs:28-90`; `migration:276-324`). La API agrega los dos mensajes iniciales del outbox en esa unidad de trabajo. El operador se elige por envío, no por membresía fija.
- **Tracking público:** `public_tracking` valida formato, calcula hash, exige enlace no revocado y vigente, y solo retorna `Estado` (`EfEnlacesSeguimientoRepository.cs:38-42`; `migration:258-274`). La función ejecuta como `public_fn`; el rol anónimo no recibe SELECT general de las tablas.
- **Outbox/Kafka/RabbitMQ:** API inserta los mensajes permitidos; worker reclama un mensaje y finaliza el lease por funciones de cola; Kafka/RabbitMQ publican solo el destino reclamado (`EfOutboxRepository.cs:18-50`, `Worker.cs:33-89`, `KafkaOutboxWorker.cs:22-48`). El consumidor RabbitMQ valida envelope y no confirma hasta commit o retry confirmado; el processor verifica el mensaje persistido y guarda seguimiento/idempotencia con actor del trabajo (`GenerarSeguimientoConsumer.cs:129-171,242-248`; `ProcesarGeneracionSeguimiento.cs:33-119`). RLS del worker limita las filas al ID de mensaje, envío y operador del job.

## Riesgo demostrado

No se reprodujo un defecto que permita cruzar tenants mediante consultas normales ejecutadas con el rol restringido y contexto puesto por el recorrido de aplicación. Sí queda demostrado un límite importante: el rol restringido puede ejecutar `set_config` para las variables de sesión personalizadas. Las pruebas de bajo nivel ponen `nexoruta.actor_kind` y `nexoruta.org_id` directamente desde una conexión con rol API (`RlsPolicyTests.cs:181-232`). Por eso RLS confía en que la API obtuvo esos valores del acceso persistido; no prueba por sí misma que el GUC sea auténtico. SQL arbitrario bajo la credencial API podría falsear el actor y consultar filas de otro tenant. El ADR reconoce este límite (`docs/alcance/ADR-MT-001-PostgreSQL-RLS.md:52`).

## Límite del diseño

- RLS filtra filas y valida filas nuevas/modificadas, pero no suplanta autenticación/autorización de negocio ni transforma un rol privilegiado en uno restringido. Los grants limitan qué comandos/columnas son posibles; `USING` y `WITH CHECK` limitan qué filas de esos comandos aplican.
- Una consulta SQL directa bajo `nexoruta_api_runtime` o `nexoruta_worker_runtime` continúa sujeta a ACL y RLS. Una consulta sin contexto no ve filas protegidas (prueba `RestrictedApiRoleCannotSeeRowsWithoutAnActorContext`, `RlsPolicyTests.cs:121-162`). La prueba con `nexoruta_api` no es una prueba de resistencia a inyección SQL: el propio rol puede fijar GUCs personalizados.
- SUPERUSER, un rol con `BYPASSRLS`, el dueño de esquema si se le concediera login/permisos adicionales, o SQL arbitrario que cambie `nexoruta.*` quedan fuera de la garantía de aislamiento entre tenants. `FORCE ROW LEVEL SECURITY` somete al dueño ordinario a políticas; no somete a superusuario ni a `BYPASSRLS`.
- Las tablas de Identity son globales, no tenant-RLS. La capa API debe limitar acceso a cuentas y hashes; RLS no evita que SQL arbitrario ejecutado con el rol API lea esas cuentas globales.
- El worker limita el mensaje/job persistido, pero el diseño no protege de un worker comprometido que ejecute SQL arbitrario y falsifique sus GUCs. Mantener los workers restringidos a los consumidores y comandos necesarios es parte del límite operativo.

## Pendiente

1. La migración usa `CREATE SCHEMA IF NOT EXISTS nexoruta_app AUTHORIZATION nexoruta_schema_owner`. Si un entorno ya tuviera esa schema creada con otro dueño, `IF NOT EXISTS` no cambia el ownership. La prueba verifica dueños de funciones, pero no hace una afirmación universal sobre el dueño de un esquema preexistente; antes de desplegar en un entorno así se debe comprobar `pg_namespace.nspowner` y corregirlo con operación/migración revisada. No se tocó la base persistente para esta auditoría.
2. El ADR de multitenancy describe `AspNetUserTokens` con UPDATE, pero el ACL final de la migración solo otorga SELECT/INSERT/DELETE. Es una diferencia documental, no un permiso UPDATE efectivo; actualizar el ADR queda pendiente fuera de `docs/rls/`.
3. No se usó PostgreSQL persistente/local ni se comprobó su catálogo actual; esta auditoría prueba la migración y roles en bases efímeras. La instalación concreta debe seguir verificándose en su proceso de despliegue.

## Hallazgos por severidad

- **Informativo — límite explícito:** GUCs mutables no son una identidad firmada; cualquier SQL arbitrario bajo el rol puede alterar el actor. Se documenta en «Riesgo demostrado» y «Límite del diseño»; no se presenta como aislamiento frente a inyección SQL.
- **Bajo — documentación desalineada:** la referencia del ADR a UPDATE sobre `AspNetUserTokens` no coincide con el ACL de la migración. No se cambió el SQL ni el ADR histórico durante esta auditoría.
- **Pendiente de entorno — propiedad previa del esquema:** `CREATE SCHEMA IF NOT EXISTS` no corrige el propietario si el schema ya existe. Debe verificarse el catálogo de cualquier destino preexistente antes de habilitar los logins de runtime.
