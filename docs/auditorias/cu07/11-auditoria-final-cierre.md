### Ambigüedad de «incluso parcial»

El resumen de Excel (`CU obligatorios!D10`) por sí solo admite más de una lectura: reimportar una parte de un archivo/lote, o aceptar parcialmente filas válidas de un archivo mixto. El PDF §5.2, p. impresa 4 / p. física 5, es más explícito: «reimportar un lote, completo o parcial» no puede duplicar envíos. La lectura respaldada es que la idempotencia cubre el lote completo y cualquier subconjunto reintentado. Ninguna fuente encontrada exige procesamiento parcial por fila cuando otras filas son inválidas. El rechazo atómico de un archivo con error/conflicto es una decisión de implementación/proyecto documentada en 06, no una frase literal de la letra; no contradice el requisito de reimportación de subconjuntos.

## Semántica observada de importación y cobertura de escenarios

El archivo se valida antes de comenzar escrituras. Todas las filas nuevas del archivo confirmado comparten una transacción; no hay commit por fila. Un archivo con cualquier fila inválida o referencia conflictiva rechaza todas las creaciones nuevas. Las identidades existentes equivalentes se informan YaExistente y no cambian; las filas nuevas válidas del archivo rechazado se informan NoProcesado. Los resultados no prometen Creado antes del commit del middleware. Una pérdida de respuesta durante commit se trata como resultado incierto; la misma referencia puede recuperar el resultado al reintentar. Cada envío nuevo produce una vez las dos filas outbox anteriores dentro de la transacción; referencias existentes y duplicados internos no producen filas adicionales.

| Escenario solicitado | Evidencia y resultado observado |
|---|---|
| CSV válido de varias filas | `Import_CreatesOnceAndRecognizesCompleteAndSubsetReimports`: creación reportada y datos persistidos con hijos/identidad/outbox del caso. |
| Archivo con filas válidas e inválidas | `Import_RejectsInvalidRowsAtomicallyAndDistinguishesExternalConflict`: HTTP 422, no crea fila válida del archivo, informa inválida/no procesada y no aumenta envíos/outbox. |
| Reimportación idéntica completa | Mismo test de creación/reimportación: no duplica y devuelve existente. |
| Reintento de subconjunto ya importado | Mismo test: subset devuelve existente sin duplicar. |
| Corrección y reintento de filas fallidas | Se agregó al test de archivo inválido el reenvío de `NEW-2` con la fila corregida: HTTP 200, `Creado=1`, total de envíos e identidades pasa de 1 a 2 y outbox aumenta únicamente en 2. Test class completo 15/15. |
| Misma referencia, contenido u operador diferente | `Import_RejectsInvalidRowsAtomicallyAndDistinguishesExternalConflict` y `Import_IsCommerceScopedAndOperatorIsPartOfEquivalenceButNotIdentity`: conflicto, no sobrescribe. |
| Referencias repetidas en el mismo archivo | `Import_CoalescesEquivalentInternalReferencesAndRejectsIncompatibleOnes`: equivalente una vez + `DuplicadoDe`; incompatible conflicto y archivo sin nuevas escrituras. |
| Solicitudes concurrentes superpuestas/en orden distinto | `Import_ConcurrentOverlappingReferencesInReverseOrderSerializesWithoutDuplicates`: creado/existente sin duplicación ni deadlock. |
| Fallo dentro del procesamiento | `Import_FailureInsideBatchRollsBackShipmentIdentityAndOutbox` (failpoints de envío/identidad/outbox): rollback integral. |
| Respuesta perdida luego del commit | `Import_RetryRecoversAfterCommitCompletedButResponseWasLost`: reintento con las mismas referencias recupera envío sin duplicar eventos. |

## Hallazgos y resolución

### H-01 — Listado de envíos denegado al rol API restringido (corregido)

- **Severidad original:** Media para Commerce; defecto adyacente al alta, no incumplimiento literal de los canales CU-07.
- **Comportamiento anterior:** `EfEnviosRepository.ListarAsync` hacía una lectura directa de `IdentidadesEnvioImportado`; al usar `GET /api/envios` con `nexoruta_api`, PostgreSQL devolvía `42501 permission denied`. La política de privilegios revocaba SELECT general correctamente, por lo que el arreglo no debía ampliar permisos.
- **Corrección presente en el checkout:** la migración aditiva `backend/src/NexoRuta.Infrastructure/Persistence/Migrations/20261030120000_ListImportedShipmentReferences.cs` crea `nexoruta_app.list_import_shipment_references(uuid[])`. La función es `SECURITY DEFINER`, fija `search_path = pg_catalog, nexoruta_app`, valida actor Comercio, usuario/acceso/comercio vigentes y restringe filas al comercio contextual. El propietario es `nexoruta_shipment_fn`; se revoca `PUBLIC` y solo se concede `EXECUTE` a `nexoruta_api`. `EfEnviosRepository.ListarAsync` obtiene las referencias llamando a la función, no con join directo a la tabla privada.
- **Regresión:** `backend/tests/NexoRuta.IntegrationTests/Seguridad/RlsRestrictedHttpFlowTests.cs`, `RestrictedCommerceHttpCanCreateShipmentAndSeeItAfterChosenOperatorSuspension`, corre con el rol API restringido y comprueba GET 200, referencia propia, falta de SELECT directo, permiso de ejecución acotado y ausencia de referencias ajenas al consultar bajo otro comercio.
- **Resultado de esta actualización:** H-01 se registra como corregido y con regresión específica bajo rol restringido. No se ejecutó esa prueba durante esta edición documental; por tanto, se describe el alcance de sus aserciones, no un nuevo resultado de ejecución. La suite de 53 pruebas de contrato reportada por el usuario tampoco sustituye una integración PostgreSQL/RLS.
- **Impacto residual:** la consulta de `Mis envíos` deja de estar bloqueada por esta denegación en el código actual; el API conserva privilegios restringidos y aislamiento. No se afirma que una imagen Docker esté enlazada a un commit exacto.

## Otras brechas, límites y ambigüedades

1. **Automatización visual histórica no concluyente; evidencia manual posterior aportada:** el comando combinado de integración/Kestrel/Commerce/Chromium tuvo 14 éxitos y 1 fallo en `CommerceCsvImportKestrelTests.KestrelAndCommerceBrowserUseIsolatedPostgresForImportAndReimport`. La excepción observada fue `IOException: The process cannot access file 'Account Web Data' because it is being used by another process` desde `CommerceCsvImportKestrelTests.cs:289`, al limpiar el perfil temporal de Chromium. El `finally` pudo enmascarar una aserción previa y los artefactos visuales no quedaron completos; la causa del incidente sigue sin determinarse. El usuario aportó después resultados manuales de los recorridos Commerce, importación y API descritos arriba. Esos resultados aportan evidencia funcional, pero no convierten el run fallido en aprobado ni son capturas realizadas por el auditor.
2. **Docker local activo, revisión de versión inconclusa:** `docker context show` devolvió `desktop-linux`; Compose mostró API/Commerce y PostgreSQL corriendo; `http://localhost:5000/health/ready` dio 200. API y Commerce no tenían bind mount de fuente ni etiqueta de revisión Git observada; los contenedores usaban imágenes con IDs `sha256:217ebee3…` (API) y `sha256:dd8ee47a…` (Commerce). El usuario informa pruebas de contrato contra la API local, pero no se vinculó la imagen servida a un commit del checkout. La salud HTTP no demuestra identidad de fuente. Esta limitación de procedencia queda explícita, sin invalidar los resultados funcionales comunicados.
3. **OpenAPI/cliente:** el contrato de multipart pasa el test de OpenAPI y el modelo binder del servidor acepta los nombres usados por ApiClient. Los nombres se serializan con casing distinto (`Archivo`/`OperadorId` en el schema y `archivo`/`operadorId` en el cliente); no se observó incompatibilidad en las pruebas del endpoint, pero conviene mantener el test de contrato y documentar la tolerancia de casing para consumidores externos estrictos. No es hoy un defecto probado.
4. **Políticas no prescritas:** formato CSV, nombres de campos, unidades, límite 5 MiB/500, referencia externa por comercio, sensibilidad a mayúsculas, huella V1, equivalencia y rechazo atómico son decisiones de producto/diseño de 06, no requisitos textuales de CU-07. La letra no define qué hacer cuando una identidad reimportada trae datos distintos; el conflicto sin actualización es la política implementada.
5. **D01:** `Dependencias!A4:I4` menciona “contexto de operador + vínculo comercio-operador”; ADR-MT-001 establece selección de operador por envío y no membresía permanente. El código valida el operador escogido y el contexto del comercio. La diferencia de formulación permanece como aclaración documental, no se impone una nueva regla de acceso.
6. **Fuera del veredicto:** un bulto por envío limita CU-08 y se deja como dependencia separada. El monitoreo integral de RabbitMQ/Kafka, backoff creciente, DLQ y todas las tareas transversales del §6.8 no se verificaron como sistema completo. Para CU-07 sí se comprobó que filas outbox se escriben de forma atómica y no se duplican en reimportación. Ningún fallo de reparto, móvil, CU-08 ni revisión nativa se usa para abrir CU-07.

## Veredicto y plan mínimo

**Veredicto: CU-07 completo para su alcance directo.** El alta individual se acredita por implementación y comprobaciones automatizadas previas, más el recorrido Commerce manual informado. El alta API se acredita por integración previa y el resultado manual comunicado para el ID señalado, con estado inicial `Admitido` y datos correctos. La importación idempotente se acredita por cobertura automatizada existente y por los resultados manuales informados: 15 nuevos, reimportación completa 0/15, y mezcla 3 existentes + 3 nuevos sin errores. La regresión H-01 está corregida en código mediante una función de lectura acotada, con prueba diseñada para el rol API restringido; no se amplió SELECT general. El usuario además informa 53 pruebas de contrato aprobadas contra el snapshot OpenAPI actualizado y la API local.

El veredicto distingue capas: los resultados manuales fueron aportados por el usuario; las 53 pruebas automatizadas también fueron comunicadas por el usuario y no se volvieron a ejecutar; los resultados Testcontainers y los fallos de Kestrel/Chromium pertenecen a cortes previos. La falla de cleanup no se marca como aprobada ni se le inventa una causa, pero deja de ser un bloqueo funcional ante la evidencia manual posterior. La imagen Docker local no quedó vinculada a un commit, por lo que el cierre no certifica la procedencia exacta del binario servido.

No queda una corrección funcional directa de CU-07 pendiente según las fuentes y evidencias registradas. Se conserva como nota documental D01 (formulación de vínculo comercio–operador frente a selección por envío) sin imponer membresía adicional. CU-08, máquina de estados completa, móvil/offline, revisión nativa y mensajería transversal permanecen fuera de este veredicto.
