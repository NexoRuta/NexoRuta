# Observabilidad de la demo GCP

Cada release incluye Compose, Prometheus, Loki, Tempo, OpenTelemetry Collector, Grafana Alloy, el collector de métricas de GCP y los archivos de provisión de Grafana. Prometheus, Loki y Tempo se ejecutan solo en la VM A; sus volúmenes viven bajo `/srv/nexoruta/docker`. Grafana corre en ambas VMs y se publica con el subdominio `monitor`.

El perfil [local](../../local/observability/README.md) levanta los mismos componentes y usa el mismo [dashboard](../../observability/grafana/nexoruta.json). En ambos entornos, Grafana usa Prometheus como única fuente de métricas, Loki para logs y Tempo para trazas.

OpenTelemetry Collector y Alloy se ejecutan en ambas VMs. Las aplicaciones envían métricas y trazas al Collector local, que reenvía métricas a Prometheus y trazas a Tempo en A. Las métricas conservan `service_name` y `node`, que usa el filtro del dashboard. Cada request web deja un evento estructurado con método, plantilla de ruta, estado y duración, sin URL completa ni cuerpo. Las llamadas HTTP salientes propagan W3C `traceparent`; los procesadores eliminan URL, query string y datos de excepción antes de exportar. Alloy lee stdout/stderr de cada contenedor mediante el Docker Engine y envía los logs a Loki, etiquetados por nodo, servicio y contenedor. Se filtran líneas con credenciales, tokens en query strings o rutas de seguimiento; `trace_id`, `span_id` y `correlation_id` quedan como metadatos estructurados.

El servicio `gcp-metrics-collector` consulta la API de Cloud Monitoring cada 60 segundos y expone las series para el scrape de Prometheus. Incluye métricas de Compute Engine, Cloud SQL, balanceador y señales personalizadas de sesión, servicios, contenedores y colas. El agente de estado de cada VM publica también el estado, reinicios y OOM de sus contenedores. Redis es un servicio esperado solo en VM B: ambos agentes comprueban su TLS, hostname, AUTH y PING; el agente de B además publica memoria usada/RSS/límite, clientes, evicciones, CPU, memoria cgroup y PIDs. No se considera la ausencia de Redis en A como incidente de contenedor. Prometheus carga las reglas compartidas de disponibilidad, HTTP 5xx/p95, workers, RabbitMQ/Kafka, sync, Push y caché desde `deploy/observability/prometheus/alerts.yaml`; el tablero muestra las alertas activas con sus etiquetas de servicio. La identidad runtime tiene `roles/monitoring.viewer`. El receiver `googlecloudmonitoring` de OpenTelemetry está en estado alpha. Más detalle operativo en el [runbook de caché Redis](../../../docs/runbooks/cache-redis-grafana.md).

Prometheus scrapea y evalúa las reglas cada 30 segundos. El dashboard de pruebas de carga también se refresca cada 30 segundos; las métricas de Cloud Monitoring conservan su recolección de 60 segundos.

Prometheus tiene un límite de memoria de 4 GiB en A. El 12/11/2026, el límite anterior de 2 GiB provocaba OOM durante la recuperación del WAL/WBL persistente y dejaba las consultas de Grafana en HTTP 503. Ante una repetición, comprobar el log del kernel, los reinicios del contenedor, la memoria disponible del host y `http://<IP privada A>:9090/-/ready` antes de intervenir. Conservar los volúmenes y los registros WAL/WBL; la retención de bloques no limita la memoria necesaria para recuperarlos. Tras la recuperación, esperar el scrape y el drenaje de las colas OTLP y comprobar muestras recientes de ambos nodos.

En ese incidente, las colas persistentes de los collectors A/B repetían muestras de varios días atrás rechazadas con `400 too old sample`, sin recuperar las series actuales. Se detuvo únicamente cada collector, se movió su directorio `prometheusremotewrite` a `prometheusremotewrite.backup-20261112` dentro del mismo volumen `nexoruta-demo_otelcol` y se reinició con una cola nueva. Los respaldos se conservan para diagnóstico; no se borraron datos de Prometheus. Esta intervención es deliberada, no una limpieza automática al arrancar ni una instrucción para reinyectar muestras antiguas fuera de la ventana admitida.

Los puertos 9090, 3100, 3200 y 4317 se publican solo en la interfaz privada de A; el firewall admite conexiones desde la subred de las VMs. Prometheus conserva siete días y un máximo de 4 GB; Loki y Tempo conservan siete días. Los datos permanecen en volúmenes del `data-root` persistente. La pila tiene un único nodo central en A, por lo que la observabilidad no está disponible mientras A está caída.
